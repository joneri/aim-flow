# One entry: requirement to contained local tests

`aim-flow.py run --config /absolute/original-work-config.json --config-sha256 SHA --state /absolute/new-run` previews one new, explicitly expanded outer grant. The existing pinned initial `work` configuration is the only project configuration input. `--authorize-intent SHA` approves the exact outer preview. Supply the existing approved provider key only for a granted invocation. No per-stage declaration, continuation config, command or container spec needs to be authored by the operator.

The distinct `aim-flow-requirement-local-run` schema-1 grant covers up to three model generations: onboarding, implementation and independent combined source review/workspace policy. It also covers one private candidate and one typed contained validation attempt. The grant binds the original requirement, source/edit/review scopes, resource catalog, immutable controller, child initial intent, campaign/history cap, provider, disclosure scope, effects and exact canonical Python executable/hash. The current interpreter is the default verifier; `--python` can choose another pinned path. Review limits default to the initial onboarding limits; `--review-output-tokens` and `--review-max-operation-nano-usd` override them explicitly and are bound into the preview.

Changing Python or limits on resume changes the grant and is refused. Old `work` or `validate-work` grants cannot authorize this outer scope. Their schemas and receipts are preserved. Initial `work` configurations are accepted as inputs, not as authority for additional phases. Initial and later phases must use the same immutable installed controller; configurations pinning an older installation are not silently migrated.

Flow internally generates exact child grants, continuation config, typed plan/declaration, independent review inputs, archive policy and container spec. It records child intents durably before dispatch, verifies completed child receipts rather than replaying them, refuses missing consumed inputs and preserves uncertain attempts for reconciliation. A missing child after recorded dispatch is an unknown outcome, not permission to retry. A terminal result is verified without repairing inputs or calling providers/containers. `--verify` performs that completed-run verification and accepts no credential or authorization.

Infrastructure/runtime/application-environment settings still come from the explicitly pinned resource catalog/templates. Flow selects and validates those supplied inputs; it does not claim it independently discovered or provisioned them. Unsupported source definitions, workspace policies, resource combinations, commands or dependencies stop with explicit needs. Ordinary credential availability is a pause under the existing outer grant, not a new per-adapter approval.

A passed local test receipt is not product or browser acceptance. Source-only unknowns, unsupported hosted CI/release work and generated-output limits remain explicit. This grant does not authorize PR creation, CI dispatch, merge, publication, deployment or production changes. A complete end-to-end release pilot remains future work.

Offline contracts use synthetic provider replies and a mocked container execution boundary with real Git, plan derivation, budget and existing receipt verification. They are not a live model, Docker, project test or browser run.

## Optional executed-evidence review

`--review-executed` creates a distinct schema-2 outer grant with at most four model generations. Without it, the existing schema-1 three-generation grant and result shape are unchanged. An old grant cannot enable this mode or capture/disclose evidence retroactively.

In this mode Flow internally enables source-cited artifact selection in the existing fresh workspace review. That policy chooses bounded PNG/JSON output paths from the actual candidate test/generator source. No artifact filenames come from the operator or infrastructure template. The existing container adapter retains and verifies their exact bytes against measured output inventory. Only a completed, verified passing continuation with complete generated outputs can enter the fourth phase.

The fourth generation independently reviews the original criteria, exact candidate/source-review evidence, runtime and stage observations, retained JSON and actual PNG pixels. The explicit outer preview authorizes disclosure of those source-selected artifacts to the same approved OpenAI provider, under the same campaign/history budget. It does not authorize new project execution, publication or deployment. Flow generates the acceptance configuration and exact dispatch intent; there is no per-stage operator configuration.

`--execution-review-output-tokens` and `--execution-review-max-operation-nano-usd` set the fourth phase limits. They default to the combined workspace-review limits and are valid only with `--review-executed`. Mode, Python and all limits remain pinned on resume and `--verify`; supply the same options. Missing credentials pause under the granted scope. Unknown/rejected/consumed review attempts never retry. Terminal verification regenerates the exact request and verifies its retained response and all upstream receipts without creating or repairing files.

The result preserves the independent adapter's `localFeatureAccepted`, `productAccepted`, `pendingDeliveryObligations` and detailed criterion/prior-obligation dispositions. It always reports `deliveryReady: false` and no publication/deployment authority. Local model-reviewed acceptance can coexist with outstanding CI/release obligations; it is not human review or completion of delivery. A failed local run never triggers the fourth model call. Missing/defective evidence produces `executed-evidence-review-blocked` rather than promoting test exit zero to acceptance.
