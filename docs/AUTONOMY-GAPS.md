# Remaining autonomy gaps

The target is a project-aware route from a requirement through implementation,
review, tests, repair and authorized delivery. The controller does not yet
provide unattended delivery for arbitrary repositories.

## Implemented pilot corrections

The repair loop iterates within the owner's shared monetary and paid-generation
authority. Severity and actual impact determine blocking findings; preexisting
low-impact collateral observations remain visible follow-ups. Verification
reuses authenticated, source-bound flat input closures instead of recursively
rerunning every historical verifier. Changed inputs invalidate reuse. Unknown
process outcomes never authorize replay. Optional metadata deadlines are explicit;
owned descendants are cleaned up without signalling a caller's process group.

Project-native host execution complements the existing container route. Onboarding
must investigate actual build, test, CI and delivery scripts and their network
needs before choosing infrastructure. A legitimate online test must not be
rewritten merely to fit an offline-only adapter. Runtime preparation retains
command completion independently of application receipts. Complete internal
package-manager hardlink groups are measured safely; external aliases and
hardlinks to private control evidence remain refused. A separate source-bound
inventory recovery can reconcile the known post-install inventory failure without
rerunning installation or rewriting the old receipt.

GitHub delivery performs exact candidate publication, guarded merge and exact
merged-main CI/artifact observation. Release continuation prepares a fresh merged
checkout and invokes the project's existing release tools. Installation alone,
model text, an intent hash or a local test pass grants no production authority.

## Requirements and verification methods

A pilot exposed a method escalation: assessment added a manual device/reader
procedure, refinement preserved it as an acceptance obligation, and later review
treated that proposed procedure as a mandatory original requirement. Future
onboarding, refinement and review instructions now distinguish original outcomes
from proposed verification methods. An unavailable nonessential method is a
clear not-performed limitation, supported by proportionate existing evidence.
Essential missing evidence is identified early. Concrete defects, integrity,
authorization and actual mandatory project gates remain binding.

An explicit owner verification-scope decision has its own source-bound receipt.
It preserves the blocked model review unchanged and records exactly which
uncertainties and evidence the owner addressed. It cannot accept failed project
execution, a demonstrated defect, missing evidence or an outstanding delivery
gate. Keyboard, labels and native-button semantics do not become a claim that a
real screen reader was used or that spoken announcements/interoperability passed.

## Runtime tools and existing authority

A private executable alias can break Git's installation-relative discovery of its
HTTPS helper. Future project-command intents qualify the canonical helper prefix
when the named Git is the same pinned executable already used for source
inspection. Helper hashes are bound and rechecked. Explicit declarations remain
explicit; historical intents retain their original semantics. No ambient PATH or
credential is inferred from this correction.

Capture actual production authority at project/task intake: owner, target,
permitted effects and exclusions. Derive exact operation grants within that
existing trusted scope, without asking again simply because a phase changed.
Missing authority should be identified before paid implementation. Never broaden
a scoped approval to another destination or effect. External tool approval review
is a separate control: repository code cannot disable it or conceal its refusal.
A rejection requires a safer authorized route or new relevant authority.

## Remaining product gaps and evidence limits

The phases still need explicit source-bound project configuration for release
selection, tools, prerequisites and protection evidence. A wrapper around manual
declarations is not automatic repository understanding. Project-native host
commands use operator privileges; they are not a hostile-code sandbox.

Operational release is not feature acceptance. HTTP success and a transport
receipt do not prove control behavior; existing production-capable browser
recipes retain their own results and limitations. Fixture API routes do not
verify production backend behavior. Native-button/label and keyboard assertions
do not establish real assistive-technology speech or interoperability.

Private operator decisions, customer sources, credentials, budgets, journals,
request/response payloads and screenshots remain outside the distributable. Local
package checks neither rerun that pilot nor authorize a new model call or release.
