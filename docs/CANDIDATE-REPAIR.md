# Explicit candidate repair

`aim-flow.py repair-candidate` is a single bounded continuation from an existing
genuine Flow producer. It does not change the old producer, original intake,
exact edit grant, rejected review, baseline, or accounting reservations.

A new configuration pins the installed controller, original producer's
`workflowConfig`, `workflowState` and `producerController`, verifier `python`,
`producerVerificationTimeoutSeconds`, original `intakeAuthority` (`intake`,
`grant`, `dispatch` pins), `rejectedReview` (`state` and all eight exact file
hashes), current `campaignBudget` pin, `maxOutputTokens`, `maxOperationNanoUsd`
and `timeoutSeconds`. The operation ceiling is checked after token counting and
before budget reservation or generation.
Its format is `aim-flow-candidate-repair`, schema version 1. Preview is read-only.
Authorize the exact preview digest with `--authorize-intent`. One proposal
generation shares the original campaign and historical USD20 liability ceiling.
The authority must be the canonical retained original intake/run/initial chain,
including its full consumed run grant, initial dispatch and result, under the
recognized intake implementation. A self-consistent replacement proof elsewhere
cannot widen the original directory boundary.

The retained completed rejection is diagnosed, never accepted. Every raw claim,
unknown and citation is retained unchanged. Citation locations are checked
individually, with invalid references retained as errors. Even a valid location
does not prove semantic support. The implementation request must independently
inspect source and preserve the original story, business assertions and test
obligations. No model shell or tools are accepted, only literal old/new edits.

A completed `review-blocked` source review with nonempty findings is also an
eligible diagnostic input. Its inventory must additionally pin `review.json`.
Flow reparses the exact completed raw response and requires both the retained
review and result to match. Findings remain observations to check independently;
this never turns blocked review into execution or acceptance authority.

An optional `parentRepair` pins the previous `producerKind: repair-candidate`,
`producerController`, `workflowConfig`, `workflowState` and `repairConfig`.
It permits one explicit second repair while `originalProducer` and
`intakeAuthority` still bind the canonical original intake. The fixed verifier
checks the prior repair and unchanged requirement, baseline, assessment,
resources and accounting. A prior config containing `parentRepair` is refused;
this is not a recursive repair loop or an upgrade of a consumed grant.

One further repair is available only with explicit `repairOrdinal:3`, exactly two
verified prior repairs and the same canonical original intake. A fourth repair
is refused. Publication independently checks every retained single-parent link
through all three repairs to the original assessed baseline.

Optional `campaignContinuation:{path,sha256}` selects an explicitly declared
combined-budget increase under the [API funding contract](API-DELIVERY.md).
Flow verifies the original producer using its unchanged original configuration
before applying the continuation to paid accounting. `campaignBudget` then pins
the new journal; the derived producer configuration retains its original budget
references. The bounded outer driver forwards the funding pin to both fresh
reviews and preserves the original journal and all prior reservations.

Local metadata verification has no default wall-clock limit. An explicit positive
`producerVerificationTimeoutSeconds` remains available without an arbitrary
upper ceiling, and `null` selects unbounded local verification. The selected
transport policy reaches nested historical verifier processes and their pure Git
reads; immutable historical code, manifests and grants retain their semantic
checks. Output memory remains bounded. Provider calls and explicitly declared
project execution resources are separate controls.

A fixed read-only verification transport records an authenticated, flat closure
of the actual inputs: file contents, permissions/link shape, queried directory
entries and native Git query results, including nested verifier dependencies.
Unchanged input reuses the successful verified transcript without running the
historical verifier again. Git objects are checked in batches. Missing or changed
input forces fresh verification; invalid authentication refuses reuse. Unknown
native operations, actual writes and failed outcomes are never cached. The
private evidence store sits outside the immutable controller inventory. Canonical
campaign journals may append validated reservations outside the producer states;
old rows, funding identity and pinned historical budget files remain protected.

Opaque-literal rejected sources are rederived from exact unchanged Git bytes and
their complete projection metadata. Changed sources or forged displays are
refused. Hidden values remain withheld and unqualified, and all diagnostic
claims remain untrusted.

The new exact edit scope is derived from source-bound candidate finding paths
and committed node entrypoints of the assessed validation stages, inside the
original explicit allowed directories. Assessed definitions, onboarding sources
and credential paths remain protected. The preview lists this new scope and
exclusions. This never upgrades the old exact edit grant.

Both original and repair implementation proposals
are reparsed from the exact completed provider response against committed source,
with response identity/status/model/usage reconciled to paid campaign accounting.
An altered proposal plus altered local self-hashes cannot replace that output.

After verifying this provenance, Flow creates a private single-parent descendant of
the original Flow candidate. Its source receipt retains the original assessed
baseline and full accumulated diff. No tests or publication run in this phase.
A fresh valid independent review remains mandatory.
Assessment reuse is derived across the original assessed baseline to the repaired
commit, comparing every original assessment source's Git object and mode. Any
changed evidence remains `fresh-candidate-assessment-required` and blocks the
existing validation gate; the fixed producer verifier rechecks this field.

Repair scope uses raw source-bound assessed stages, preserving unresolved/manual
predecessors and agent unknowns as diagnostics. It does not require an
execution-ready graph merely to inspect source. Later validation still requires
the existing fresh review and execution-plan refinement gates.
The local grant retains the full unresolved plan. Provider requests retain
source-backed needs, statuses, unsupported steps and unknowns, but project
resource candidates through the existing public-capability whitelist. Local
execution-spec paths, identities and operator metadata are not disclosed;
configured capabilities are not claimed as measured runtime qualification.

`--verify` is read-only and takes no credential or authorization. Missing,
drifted or uncertain consumed inputs fail closed and are never reconstructed.
Interrupted generation/private Git effects are not replayed.

For `validate-work` or `resume-candidate`, use `producerKind: repair-candidate`,
the original repair configuration's `repairConfig` pin, `workflowState` pointing
to the completed repair state, and `workflowConfig` pointing to its exact
`derived-workflow-config.json`. The producer controller is the repair controller;
the original project-instance controller remains separately pinned. A fixed
`repair-candidate --verify` subprocess confirms this provenance. Ordinary
producer contracts remain unchanged. The publication bridge preserves the repair
configuration and invokes the same fixed repair verifier, independently checking
both parent links and the full original-baseline diff. No repair or validation
grant authorizes publication; the delivery chain still requires completed local
acceptance and a new exact GitHub phase grant.

Offline synthetic tests exercise the fixed verifier, literal edits, ancestry,
rejection/accounting preservation, exact new scope and refusal/replay behavior.
They are not evidence of a live provider repair, browser pass or product acceptance.

## One Flow-owned local continuation

`aim-flow.py repair-and-validate` wraps repair and the existing resumed local
validation workflow under one new exact grant. Its configuration format is
`aim-flow-repair-local-run`, schema version 1, with `manifestSha256`, the pinned
`repairConfig`, and `reviewMaxOutputTokens`, `reviewMaxOperationNanoUsd`,
`executionMaxOutputTokens`, `executionMaxOperationNanoUsd`. Flow derives child
states `repair` and `reviewed` and every later configuration and intent. Operators
do not author child dispatches or rewrite the old intake, baseline or review.
Optional `reviewEvidencePolicy` is checked and forwarded to the resumed child.
Optional `findingDispositionPolicy: severity-and-impact-v1` is also checked and
forwarded to the resumed source and executed reviews. Non-blocking follow-ups do
not trigger another repair or a loop; genuine blockers still stop the driver.

The read-only preview binds the complete repair intent, derived resume
configuration, original requirement/baseline/resources and unchanged shared USD20
ceiling. Authorize that exact digest with `--authorize-intent`. The grant allows
at most one repair generation, two fresh review generations and one contained
validation attempt. A fresh source/workspace review and execution-plan refinement
must pass the existing gates before tests. The executed-evidence review receives
only bounded source-selected retained JSON bytes and PNG pixels. No missing
acceptance obligations or unresolved plan gaps are removed to force execution.

Any rejection or blocker stops this continuation; there is no second repair.
Persistent dispatch markers prevent replay of unknown effects. Missing consumed
inputs, completion evidence or reservations fail closed instead of being rebuilt.
All three new paid reservations remain in the original append-only campaign.
Outer state must be disjoint from the complete original intake/run tree,
controllers, project source and accounting.

`--verify` takes no credential or effect authorization, verifies both retained
child chains and never dispatches work. A completed result can also be read again
without credentials. The result is local evidence, not publication, deployment,
business acceptance or a general autonomous loop. Its completed resumed child
can supply the separately granted delivery chain's verified local evidence.

`test_repair_run.py` uses real installed verification subprocesses, private Git
candidates and accounting, with synthetic provider and container adapters. It
covers the complete local chain, exact authorization, read-only replay, rejected
reviews, unknown effects, missing evidence and reservation continuity. This is
not a live provider repair, real container or browser pass, or product acceptance.

## General ancestry and failed execution diagnostics

Repair ancestry has no fixed depth ceiling. Flow walks pinned configurations and
Git parent links iteratively, rejects cycles and checks the exact original intake,
requirement, accounting and baseline at every link. A declared `repairOrdinal`
must match the actual ancestry; changing the ordinal cannot grant another repair.
The publication verifier follows the same complete ancestry without a four-link
special case.

Optional `failedValidation` pins a controller `{path,manifestSha256}`, an exact
container `state`, its `intent` and `result` file pins, and up to eight sorted
`contextPaths`. Flow verifies the retained container receipt, completed terminal
observation, confirmed cleanup, exact candidate, pinned runner and paid review
reference. At least one actual failed project stage and an in-bounds committed
stack location are required. Observations, failure text and stack locations are
untrusted diagnostics, never proof that an assertion is correct or acceptance.

Additional committed context is disclosed only under the new repair grant, within
the original allowed nonsecret directories and existing protected-path rules.
It is kept separate from the historical paid review. The model must independently
distinguish a real defect from a stale test assumption and preserve useful tests.
Low-priority unrelated follow-ups do not become required repairs.
The new repair request keeps context only for selected repair paths and the
original editable feature paths; complete editable files are still supplied.
The complete old paid review remains locally verified and unchanged. References
to other undisclosed files remain untrusted unknowns for the repair model. This
keeps relevant imported layout/style source affordable without resending the
aggregate gate's unrelated backend context; subsequent independent source and
executed-evidence reviews still use their complete selected input closure.

Diagnostic source review may have been paid by a later continuation of the same
budget. Flow checks that actual journal and the complete pinned funding ancestry,
without moving, refunding or duplicating its charge. The new repair uses its own
explicitly selected existing allocation; fresh review and execution remain required.

## Budget-governed orchestration (schema 2)

`repair-and-validate` schema 2 begins with a completed candidate through a pinned
`resumeConfig`, a pinned `repairTemplate`, sorted `repairContextPaths` and an
explicit `maximumNewGenerations`. It repeatedly runs fresh source review,
isolated project validation and fresh evidence review. A verified blocking
source, runtime or evidence failure derives a new source-bound repair and another
review iteration. Nonblocking findings remain follow-ups. There is no repair
count cap; the canonical funding ceiling and user's paid-step grant govern work.

Flow checks that enough unreserved budget and paid steps remain for the next
complete cycle. A reservation guard also enforces the user's count at the actual
API reservation boundary. Phase configs, dispatches and results are retained
individually; unknown, denied or incomplete effects stop without replay. Schema 1
retains its historical one-repair interpretation. A successful schema-2 result
points to the genuine reviewed child used by the normal delivery pipeline and
never grants publication or deployment by itself.
